# UI and E2E coverage matrix

This matrix tracks **critical user scenarios**, not source-code line coverage. The percentages are a manual estimate: covered scenarios divided by the small set of critical scenarios listed for each area. They are intended to identify gaps during the React migration; they are not generated by an instrumentation tool.

The tracked scenarios are the main success path plus one important boundary for each feature: empty data, unsupported capability, network failure, persistence/reload, or cleanup. A scenario is counted as covered only when a test asserts a user-visible outcome or an externally observable persisted result. Pure data transformations remain unit tests and are not counted as UI scenarios.

The uncovered scenarios remain explicit follow-up candidates. Add focused tests when those flows are changed or when failures show they need stronger release protection; avoid expanding the slow E2E layer for behavior already covered by unit or UI tests.

## Testing pyramid

- **Unit:** cover deterministic behavior such as storage preferences, calculations, transformations, update transactions and error states. Keep most cases here; current suite has hundreds of unit tests.
- **UI:** use Playwright to cover representative interaction flows and accessibility-visible outcomes. Prefer roles and labels over CSS classes and legacy IDs where possible.
- **E2E:** keep a smaller set around the boundaries that unit/UI mocks cannot prove: Service Worker lifecycle, offline cold start, persistence across reloads and version migration.

## React migration guardrails

For each legacy section migrated to React:

1. Keep or add one UI test for its main success path and one for an important empty/error state.
2. Assert the visible result through accessible roles, names and text.
3. Add an ownership assertion for the migrated section: its content and controls are rendered by React, and the old static node/imperative event binding has been removed.
4. Remove selectors tied only to the replaced legacy markup after the replacement is merged.

The matrix should be recalculated when a tracked critical scenario changes. Do not interpret its percentages as line coverage; add a coverage provider separately if line/branch metrics become a release gate.
